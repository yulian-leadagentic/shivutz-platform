# §5 · שלב 3 · Webhook ואידמפוטנטיות

`POST /webhooks/cardcom-recurring` — ליד ה-webhook הקיים.

🔴 **שלוש דרישות שאין עליהן פשרה:**

1. **אימות חתימה.** `CARDCOM_WEBHOOK_SECRET` קיים ב-`.env`. **בקשה לא חתומה → 401, בלי לגעת בשום דבר**
2. **אידמפוטנטיות.** Cardcom שולח אותו אירוע שוב. **טבלת `payment_events` עם `UNIQUE` על מזהה העסקה** — אירוע שנראה כבר מוחזר `200` **בלי לחייב שוב ובלי להאריך שוב**
3. **הנתיב ציבורי בגייטוויי** — כמו `/api/webhooks/vonage` (`gateway/src/index.js:161`). **החתימה היא האבטחה, לא הטוקן**

> **בלי אידמפוטנטיות, retry של Cardcom = חיוב כפול או מנוי כפול.** זה לא תרחיש קצה — זו התנהגות רגילה של ספקי סליקה.

# §6 · שלב 4 · חידוש

**התשתית לתזמון כבר קיימת ובשימוש:** `services/notification/src/index.js:46-88` מריץ `node-cron` יומי 06:00–08:45, וה-handlers קוראים ל-`/internal/*-batch` ב-user-org. **העתק את הדפוס. אל תמציא מנגנון שני.**

```
POST /payments/internal/renewal-batch
  → מנויים active עם current_period_end <= NOW()
  → charge_token
  → הצליח: +30 יום · נכשל: past_due + rebill_attempts += 1
```

- **latch לפני החיוב.** סמן `last_renewal_attempt_at` **לפני** הפנייה ל-Cardcom, כך ששתי הרצות מקבילות לא יחייבו פעמיים
- **`LIMIT` על האצווה.** אצווה ללא גבול שנתקעת באמצע היא מצב לא ידוע
- **כל ניסיון נכתב ל-`payment_events`** — הצלחה וכישלון
